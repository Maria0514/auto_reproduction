## 0. 立项依据：修复循环的三个失控点（去重声明）

### 0.1 与 Sprint 6 已处置缺陷的去重

sp6 已处置的 no_metrics / 规划质量族（S6-04 no_metrics 专属处置 + 早停、S6-05 计划自洽交叉检查、MF-3/4/7 观测补口，见 TODO :376、sp6 PRD §3）治的是"**命令全成功但零指标**"这一类判定与观测缺陷，以及 no_metrics 情形下的**早停转决策**（连续 N 轮 no_metrics 无进展→停自动循环转 interrupt#2）。

**本 PRD 的三个失控点与之不同、不重复立项**：sp6 的早停是"no_metrics 特定类别"的早停，早停后走的正是 interrupt#2（这条路径 sp6 已打通）。本 PRD 治的是**与错误类别无关**的三个更底层的失控点：

- **S7-01（预算耗尽绕过升级）**：`retry_budget_remaining` 预算耗尽时，代码在进入任何 interrupt#2 判定之前就 `return` 走了静默降级，**任何错误类别都会命中**（不限 no_metrics），且**绕过 interrupt#2**。sp6 no_metrics 早停判定在预算门**下方**、根本轮不到执行，治不到它。
- **S7-03（子上限冲过头）**：sp6 的早停 N 和本 PRD 的 `MAX_DEV_LOOP_LLM_CALLS` 都是"轮边界"级刹车，都拦不住单轮 ReAct 子图内部一口气烧。sp6 没触及这个机制层缺陷。
- **S7-02（coder 看不到真报错）**：sp6 MF-7 补的是"决策面板给用户贴 stdout 尾部"（人看的），本条治的是"coder 修复反馈里的 stderr 链路"（机器/agent 看的），两条链路不同、落点不同。

三点是并列新增，与 sp6 已处置项不重叠。

### 0.2 缺陷定性

**S7-01 是 PRD 级设计决策写反**（详见 §0.3~0.5）；**S7-03 是机制层缺陷**（刹车装在错误的粒度上，§0.6）；**S7-02 是信息链路 bug**（构造/取值链路错，非 coder 能力问题，§0.7）。三者共同构成"修复循环在反复失败时的失控"：修不好（S7-02 看不到真错）→ 越修越烧（S7-03 拦不住）→ 烧光了还瞒着用户（S7-01 静默降级）。

### 0.3 S7-01 根因：入口预算门反向绕过 interrupt#2

系统本有 interrupt#2（`dev_loop_failure` 决策面板，三态：重订计划 revise_plan / 降级导出 export_code / 终止 terminate），设计意图是"修复循环反复失败→中断问用户"。但 `core/nodes/execution.py:2028-2030` 有一道**入口预算门**：

```python
if budget < DEV_LOOP_MIN_CALLS_PER_ROUND:
    return _mark_degraded_for_report(updates, state, reason="budget_exhausted")
```

注释明写"不 interrupt（§2.5.4 / PRD §5）"。这是**PRD 级设计决策**（注释直接引架构 §2.5.4 / PRD §5），不是笔误。

**逻辑正好反了**：
- 预算**没**耗尽、因别的原因停（fix_count 触顶 / 不可修复 / 子预算触顶 / no_metrics 早停）→ 会走 interrupt#2 问用户。
- 预算**耗尽**（即"反复失败到山穷水尽"这个**最**该升级人工的场景）→ 命中入口门直接 `return`，静默降级出报告，用户**从不被问**。

### 0.4 S7-01 根因的当前代码路径（按实际代码校准，供架构师避坑）

需要如实校准一处转述：interrupt() 的实际触发**不是**"预算门下方那段代码顺序执行到"，而是经由 self-loop 重入的**两段式**（sp6 为满足重跑幂等契约 S-1 引入）：

1. `execution.py:2028-2030` 入口预算门：`budget < DEV_LOOP_MIN_CALLS_PER_ROUND` 命中 → `return` 走 `_mark_degraded_for_report`（`_dev_loop_route` 未置 await → `graph.py:157` 兜底路由到 reporting）。**这一步就是缺陷发生点：命中即静默降级，后续 interrupt 逻辑全部不执行。**
2. 若未命中预算门、走到 `execution.py:2051-2063`（修复耗尽/不可修复/子预算触顶）：先置 `_dev_loop_route="await_dev_loop_interrupt"` 并 `return`（commit 边界落盘，**尚未** interrupt）。
3. `graph.py:144-145` 路由 `await_dev_loop_interrupt` → self-loop 重入 execution。
4. 重入后 guard 命中跳过 sandbox，才在 `execution.py:2091` 函数体内真正 `interrupt(...)`。

结论对定性无影响（预算门确实拦在所有 interrupt 逻辑之前），但对**修正方向的实现**有影响：不能按"把 interrupt 挪到预算门上方"这种线性理解去改，那会破坏 self-loop 重跑幂等契约（S-1 / L-C3-01 命门，`graph.py:129-133`）。预算耗尽要升级人工，必须复用同一条 commit-边界-return + self-loop-重入 的两段式路径，而不是在预算门处直接 `interrupt()`。这一点作为约束交架构师（Q-S7-2）。

### 0.5 实测坐实（thread task-99eef17bccf2，checkpoints.db 最终 state）

- `fix_loop_count=4`，`fix_loop_history` 4 条全 `category=import`
- `retry_budget_remaining=0`
- `_dev_loop_llm_calls=92`（> `MAX_DEV_LOOP_LLM_CALLS=60`，**超上限 32**——此即 S7-03 的直接证据）
- `execution_result.success=False`
- **`user_fix_decision=None`**（用户全程未被问——S7-01 的直接证据）
- `current_step=reporting`，`degraded_nodes=[resource_scout, execution]`

即：import 错误反复修不好 → 烧光预算（92 次 LLM 调用，冲过 60 上限）→ 静默降级出报告 → 用户从头到尾没被问过一次。这一个 thread 同时坐实 S7-01、S7-02（4 轮全 import 修不好）、S7-03（烧过头）三点。

### 0.6 S7-03 根因：子上限只在轮边界检查，单轮内无法刹车

`MAX_DEV_LOOP_LLM_CALLS`（`config.py:112-114`，现值 60）声明是"修复循环子预算天花板"。但 `execution.py:2036` 的 `dev_calls < MAX_DEV_LOOP_LLM_CALLS` 判定发生在**轮边界**——即"进入下一轮修复回合前"才检查是否触顶。单轮 execution 内嵌 ReAct 子图一旦进入，就会一口气烧二三十次 LLM 调用（受 `REACT_MAX_ROUNDS_*` 约束但那是轮次不是调用），**中途没有任何刹车机制**。于是实测跑到 92（预期上限 60）、冲过头 32。

**翻倍治标不治本**：变更1 把 `MAX_DEV_LOOP_LLM_CALLS` 翻到 120 后，冲过头的绝对量可能更大（子图单轮烧的量不因上限翻倍而变），"轮边界才检查、单轮内无法刹车"这个机制问题原封不动。所以 S7-03 与"翻倍"是两件事：翻倍是给余量，S7-03 是修刹车粒度。

### 0.7 S7-02 根因：coder 修复反馈里全程看不到真实报错（信息链路 bug）

**坐实证据**（推翻 v0.1 "能力增强应等评测数据"的 backlog 理由）：模拟 coder 修复回合实际收到的反馈里——

1. `error_category` 只有一句笼统提示"import 错误（缺包/模块路径错误）"（`execution.py:1658` 一带的 `fix_hint=msg` 即这类笼统串）；
2. `stderr_tail` 取 logs 尾部 2000 字符（`execution.py:1121` `stderr_tail: _tail(logs)`），但**尾部恰是后续成功步骤的 stdout**——实测该 tail 里**不含** "No module named 'src'" 这个真正的报错行；
3. `representative_stderr=None`（`execution.py:1658-1659`、:2252-2253 均构造为空 `representative_stderr=""`）——代表性 stderr 片段根本没填。

三条叠加：**coder 全程看不到真实报错**。这不是 coder"能力弱修不好"，是系统把真报错在传给 coder 之前就丢了/截错了——**信息链路 bug**。checkpoints.db 中 `No module named 'src'` 出现 831 次，正是"看不到真错→每轮瞎修→同一个错反复出现"的直接后果。

**Maria 拍定方案**（写死为 S7-02 需求方向）：把"系统替 coder 决定看哪 2000 字"改成"给 coder 入口让它自主探索"——
- execution 每轮把**完整日志落盘成文件**（放 `code_output_dir` 下）；
- coder 修复反馈把截断的 `stderr_tail` 换成**日志文件路径** + 保留 `error_category` 快速提示；
- coder 用**现有 `read_code_file` 工具**自读完整日志、自主定位错误。
- 理念=最小改动（复用现有读文件工具，不新造观测管道），把截断决策权交还给 agent。日志落盘确切位置/是否需新工具/文件命名与轮次编号，交架构师（Q-S7-5）。

### 0.8 作品集 / 面试价值定位

本项目是 Maria 2026 秋招 agent 开发岗作品集（面试价值一等权重，观测性 / 人在回路 / 成本治理类价值高）。本治理族的讲点：**"修复循环失控"的系统性诊断与治理**——从"该问人时问人"（S7-01，HITL 升级点），到"想拦要拦得住"（S7-03，成本护栏的刹车粒度），到"给 agent 看真相而非替它截断"（S7-02，agent 上下文/工具自主探索的设计取舍）。这一族与 sp6 的 HITL 主题（不死锁/不失忆/不失联）一脉相承，补上"不失控"，并与 Sprint 7 成本追踪主题天然咬合（预算耗尽与子上限都是成本护栏的触发/刹车边界）。S7-02 的"日志文件路径换截断 stderr、让 coder 自读"是一个很好的 agent 设计取舍面试讲点（"别替 agent 决定看什么，给它入口"）。

### 2.2 S7-01 预算耗尽纳入 interrupt#2 人工升级（P0）

**背景 / 问题**（§0.3~0.5 已坐实）：`execution.py:2028-2030` 入口预算门在预算耗尽时直接 `return` 静默降级，绕过 interrupt#2。后果是"反复失败到山穷水尽"这个最该升级人工的场景，用户从不被问（实测 thread task-99eef17bccf2：4 轮 import 全败、92 次 LLM 调用烧光预算、`user_fix_decision=None`、直接出报告）。设计意图（interrupt#2 = 修复循环反复失败→问用户）与实际行为（预算耗尽→静默降级）南辕北辙。翻倍（§2.1）只是把掐断点推后，不改变"耗尽后静默降级"这个错误处置——所以翻倍**不替代**本条。

**需求描述**（行为契约）：

1. **预算耗尽（`budget < DEV_LOOP_MIN_CALLS_PER_ROUND`，翻倍后阈值为 4）不再静默降级**：该情形必须走**人工升级**，把决策权交还用户，而非替用户默认降级出报告。
2. **复用既有 interrupt#2 通道与两段式路径**：不新增 interrupt 种类（沿 sp6 "interrupt 种类集合不变"红线）。预算耗尽情形须经 commit-边界-return + self-loop-重入 的既有两段式抵达 `interrupt()`，不得在预算门处直接 `interrupt()`（保重跑幂等契约 S-1，见 §0.4、Q-S7-2）。
3. **决策面板须让用户感知"预算已耗尽"的终态语境**：面板文案须明确告知"修复已反复失败、重试预算已耗尽"，而非通用失败文案（沿 sp6 AC-S6-10 早停轮次上下文文案的既有做法——走既有 `summary`/`fix_hint` 通道喂 payload，零新 payload 键）。
4. **复用现有 interrupt#2 三态、不新增"追加预算"第四态**（Maria 反过度工程 + 预算已翻倍，见 §2.1 末、A-S7-1）：把"接受降级"映射到 export_code、"重来"映射到 revise_plan、"放弃"映射到 terminate。三态足以覆盖预算耗尽后的用户意图。
5. **成本硬约束不可破（对齐翻倍新值）**：`MAX_TOTAL_LLM_CALLS`（=240）/ `MAX_DEV_LOOP_LLM_CALLS`（=120）这类全局硬上限必须始终生效，绝不能突破硬顶。

**验收标准**：AC-S7-01 ~ AC-S7-04、AC-S7-06。

**非目标**（S7-01 不做）：

1. 不做"预算耗尽降级"与"其它原因降级"的差异化报告标注体系——沿用既有降级声明链路（sp5 S5-01/S5-04 通道）。
2. 不改预算的计量算法（口径不变），只改"耗尽后的处置"与"额度大小"（翻倍）。
3. 不做撤销/改主意通道——沿 sp6 非目标 4，一次决策即生效。
4. 不加"追加预算"第四态（Maria 已明确不加）。

### 2.3 S7-02 修复循环 coder 看得到真报错（P1）

**背景 / 问题**（§0.7 已坐实为信息链路 bug）：coder 修复回合实际收到的反馈里，`error_category` 只有笼统一句、`stderr_tail` 取到的是后续成功步骤 stdout（不含真报错行）、`representative_stderr=None`——coder 全程看不到真实报错，反复瞎修（`No module named 'src'` 出现 831 次）。这是系统在传给 coder 前就把真报错丢了，非 coder 能力问题。

**需求描述**（Maria 拍定方案，最小改动）：

1. **execution 每轮把完整日志落盘成文件**，放 `code_output_dir` 下（确切路径/命名/轮次编号交架构师 Q-S7-5）。
2. **修复反馈把截断的 `stderr_tail` 换成日志文件路径** + 保留 `error_category` 快速提示：coder 收到的不再是被系统截断的 2000 字，而是"完整日志在这个文件 + 一句快速提示"。
3. **coder 用现有 `read_code_file` 工具自读完整日志、自主定位错误**——不新增观测工具/管道（若架构师论证现有工具读不了该路径需微调，作为 Q-S7-5 子问）。
4. 理念红线：**把"系统替 coder 决定看哪 2000 字"改成"给 coder 入口让它自主探索"**——这是本条的设计取舍本质，实现不得倒退回"系统再挑一段塞给 coder"。

**验收标准**：AC-S7-05、AC-S7-07。

**非目标**（S7-02 不做）：
1. 不改 coder 的修复策略/prompt 结构本身（最小化编辑 vs 整份重生成不在本条范围）——本条只保证 coder"看得到真相"，看到之后怎么修是既有能力。
2. 不新造日志观测管道/新工具（复用 `read_code_file`）。
3. 不动决策面板给用户看的 stdout 尾部（那是 sp6 MF-7 的人向链路，与本条 agent 向链路正交，两者互不改动）。

### 2.4 S7-03 修复子上限拦得住（P1）

**背景 / 问题**（§0.6 已坐实为机制层缺陷）：`MAX_DEV_LOOP_LLM_CALLS` 子上限只在**轮边界**检查（`execution.py:2036`），单轮 ReAct 子图内部一口气烧二三十次调用无中途刹车 → 实测冲到 92、超上限 60 达 32。翻倍到 120 后机制问题不变（治标不治本）。

**需求描述**（行为契约，不预设实现）：

1. **修复子上限须能在单轮 ReAct 子图内部生效**，而非只在轮边界——当 `_dev_loop_llm_calls` 逼近 `MAX_DEV_LOOP_LLM_CALLS` 时，子图应能及时停止继续烧，冲过头的幅度须被约束在一个确定性小范围内（可接受的越界上界交架构师定，Q-S7-6）。
2. **刹车触发后走既有升级/降级路径**，不新增 interrupt 种类：子上限触顶本就是 interrupt#2 的既有触发原因之一（`execution.py:2077` "子预算触顶"），本条只保证"触顶被及时发现"，触顶后的处置沿用既有。
3. **不改计量口径**：`_dev_loop_llm_calls` 怎么累加不变，只补"逼近上限时的刹车检查点"。
4. 与翻倍解耦：翻倍是 §2.1 的额度调整，本条是刹车粒度修复，两者独立验收（翻倍后仍须验证 S7-03 的刹车生效）。

**验收标准**：AC-S7-08。

**非目标**（S7-03 不做）：
1. 不追求"精确不越界一次不差"——ReAct 子图内检查点有天然粒度，产品要求是"约束在确定性小范围内"，不是"零越界"（避免过度工程做逐调用拦截）。
2. 不改 `REACT_MAX_ROUNDS_*` 轮次上限语义（那是轮次不是调用数，正交）。

## 4. 需求裁决说明（v0.1 → v0.3 的范围变化）

v0.1 曾把附A/附B 列 backlog，理由是"能力增强、应由评测数据驱动"。**v0.2 起推翻此裁决并经 v0.3 收敛**，理由如下：

- **附A → S7-02（转正 P1）**：坐实证据（§0.7）表明它不是"能力增强/效果优化"，而是**信息链路 bug**——coder 根本看不到真报错。bug 不需要评测数据驱动、可直接确定性修复（构造 import 现场即可验证），backlog 理由（缺度量基线）不成立。且 Maria 已拍定最小改动方案（复用 `read_code_file`，不新造管道），量级可控、不稀释 P0。
- **附B：Maria 决定不做（完全砍掉、不进 backlog）**：S7-02 已让 coder 在 execution 报错后自读完整日志、自主定位 import 错误，"生成后进 sandbox 前再加一道 import 预检"在 S7-02 之上属多余——直接砍掉避免过度工程（符合 Maria 反过度工程一贯原则）。此项不再作为需求、不作为 backlog、不再出现在本 PRD 后续任何章节。
- **新增 S7-03（P1）**：实测烧 92 超 60 上限 32，是**机制层缺陷**（刹车粒度错），有直接现场证据、不依赖评测数据，与预算翻倍解耦（翻倍治标不治本）。纳入本治理族而非另起 PRD，因它与 S7-01 共享"修复循环失控"的成本护栏语境。

**一句话**：v0.1 的 backlog 裁决基于"这俩是能力增强、缺基线"的判断；拿到坐实证据后确认附A 是信息链路 bug（可确定性修，转正 S7-02）、S7-03 是机制缺陷（有实测，新增）；附B 在 S7-02 根治 import 可见性之后属多余，Maria 决定不做。

## 7. 拆分建议（依赖顺序，批次边界逐批确认制在开发计划执行）

1. **翻倍独立批（§2.1）**：13 常量翻倍 + 十几处硬编码断言同步改 + 全量回归——建议作为独立止血/参数批先行（改动集中在 config.py + 断言，风险可控、与其它需求解耦）；沿 sp6 "断言只换不弱化"纪律。

## 8. 产品结论小结（四段式）

- **当前理解**：Sprint 7 在已立项的"评测体系 + token/成本追踪"之外，**并列新增**一个**修复循环失控治理族**（S7-01~03）。主线 S7-01（P0）：预算耗尽被入口预算门反向绕过 interrupt#2、静默降级出报告、用户从不被问（实测 thread task-99eef17bccf2），配套预算 13 常量全翻倍（给余量、不替代升级）。P1 两条：S7-02（coder 修复反馈全程看不到真报错的信息链路 bug，改传日志文件路径让 coder 自读）、S7-03（子上限只在轮边界检查、单轮内冲过头烧 92 超 60，补刹车粒度）。附B（验证门升级）Maria 决定不做——S7-02 已根治 import 可见性，验证门多余。
- **待确认问题**：Maria 侧无（假设 A-S7-1~7 已内置留档，均可单点推翻；尤其 A-S7-1 明确不加第四态 / A-S7-3 附A转正 + 新增 S7-03 + 附B 砍掉两条）；架构侧 Q-S7-1~6（复用三态确认、两段式实现路径、翻倍派生依赖核查、面板文案落点、日志落盘落点、刹车粒度与越界上界）。
- **需求结论**：3 条需求（S7-01 P0 含翻倍 / S7-02 P1 / S7-03 P1），AC-S7-01~08（以现场同构 thread 为强制回归靶、AC-S7-05/07 须验红）。产品红线：不新增 interrupt 种类、不加第四态、复用两段式保幂等契约、成本硬上限对齐翻倍新值绝不可破、S7-02 复用现有读文件工具不新造管道、S7-03 不改计量口径只补刹车、最小单一抽象。本治理族与 Sprint 7 评测+成本追踪并列，不覆盖不吞并。
