## 0. 立项依据：修复循环的三个失控点（去重声明）

### 0.1 与 Sprint 6 已处置缺陷的去重

sp6 已处置的 no_metrics / 规划质量族（S6-04 no_metrics 专属处置 + 早停、S6-05 计划自洽交叉检查、MF-3/4/7 观测补口，见 TODO :376、sp6 PRD §3）治的是"**命令全成功但零指标**"这一类判定与观测缺陷，以及 no_metrics 情形下的**早停转决策**（连续 N 轮 no_metrics 无进展→停自动循环转 interrupt#2）。

**本 PRD 的三个失控点与之不同、不重复立项**：sp6 的早停是"no_metrics 特定类别"的早停，早停后走的正是 interrupt#2（这条路径 sp6 已打通）。本 PRD 治的是**与错误类别无关**的三个更底层的失控点：

- **S7-01（预算耗尽绕过升级）**：`retry_budget_remaining` 预算耗尽时，代码在进入任何 interrupt#2 判定之前就 `return` 走了静默降级，**任何错误类别都会命中**（不限 no_metrics），且**绕过 interrupt#2**。sp6 no_metrics 早停判定在预算门**下方**、根本轮不到执行，治不到它。
- **S7-03（子上限冲过头）**：sp6 的早停 N 和本 PRD 的 `MAX_DEV_LOOP_LLM_CALLS` 都是"轮边界"级刹车，都拦不住单轮 ReAct 子图内部一口气烧。sp6 没触及这个机制层缺陷。
- **S7-02（coder 看不到真报错）**：sp6 MF-7 补的是"决策面板给用户贴 stdout 尾部"（人看的），本条治的是"coder 修复反馈里的 stderr 链路"（机器/agent 看的），两条链路不同、落点不同。

三点是并列新增，与 sp6 已处置项不重叠。

### 0.2 缺陷定性

**S7-01 是 PRD 级设计决策写反**（详见 §0.3~0.5）；**S7-03 是机制层缺陷**（刹车装在错误的粒度上，§0.6）；**S7-02 是信息链路 bug**（构造/取值链路错，非 coder 能力问题，§0.7）。三者共同构成"修复循环在反复失败时的失控"：修不好（S7-02 看不到真错）→ 越修越烧（S7-03 拦不住）→ 烧光了还瞒着用户（S7-01 静默降级）。

### 0.3 S7-01 根因：入口预算门反向绕过 interrupt#2

系统本有 interrupt#2（`dev_loop_failure` 决策面板，三态：重订计划 revise_plan / 降级导出 export_code / 终止 terminate），设计意图是"修复循环反复失败→中断问用户"。但 `core/nodes/execution.py:2028-2030` 有一道**入口预算门**：

```python
if budget < DEV_LOOP_MIN_CALLS_PER_ROUND:
    return _mark_degraded_for_report(updates, state, reason="budget_exhausted")
```

注释明写"不 interrupt（§2.5.4 / PRD §5）"。这是**PRD 级设计决策**（注释直接引架构 §2.5.4 / PRD §5），不是笔误。

**逻辑正好反了**：
- 预算**没**耗尽、因别的原因停（fix_count 触顶 / 不可修复 / 子预算触顶 / no_metrics 早停）→ 会走 interrupt#2 问用户。
- 预算**耗尽**（即"反复失败到山穷水尽"这个**最**该升级人工的场景）→ 命中入口门直接 `return`，静默降级出报告，用户**从不被问**。

### 0.4 S7-01 根因的当前代码路径（按实际代码校准，供架构师避坑）

需要如实校准一处转述：interrupt() 的实际触发**不是**"预算门下方那段代码顺序执行到"，而是经由 self-loop 重入的**两段式**（sp6 为满足重跑幂等契约 S-1 引入）：

1. `execution.py:2028-2030` 入口预算门：`budget < DEV_LOOP_MIN_CALLS_PER_ROUND` 命中 → `return` 走 `_mark_degraded_for_report`（`_dev_loop_route` 未置 await → `graph.py:157` 兜底路由到 reporting）。**这一步就是缺陷发生点：命中即静默降级，后续 interrupt 逻辑全部不执行。**
2. 若未命中预算门、走到 `execution.py:2051-2063`（修复耗尽/不可修复/子预算触顶）：先置 `_dev_loop_route="await_dev_loop_interrupt"` 并 `return`（commit 边界落盘，**尚未** interrupt）。
3. `graph.py:144-145` 路由 `await_dev_loop_interrupt` → self-loop 重入 execution。
4. 重入后 guard 命中跳过 sandbox，才在 `execution.py:2091` 函数体内真正 `interrupt(...)`。

结论对定性无影响（预算门确实拦在所有 interrupt 逻辑之前），但对**修正方向的实现**有影响：不能按"把 interrupt 挪到预算门上方"这种线性理解去改，那会破坏 self-loop 重跑幂等契约（S-1 / L-C3-01 命门，`graph.py:129-133`）。预算耗尽要升级人工，必须复用同一条 commit-边界-return + self-loop-重入 的两段式路径，而不是在预算门处直接 `interrupt()`。这一点作为约束交架构师（Q-S7-2）。

### 0.5 实测坐实（thread task-99eef17bccf2，checkpoints.db 最终 state）

- `fix_loop_count=4`，`fix_loop_history` 4 条全 `category=import`
- `retry_budget_remaining=0`
- `_dev_loop_llm_calls=92`（> `MAX_DEV_LOOP_LLM_CALLS=60`，**超上限 32**——此即 S7-03 的直接证据）
- `execution_result.success=False`
- **`user_fix_decision=None`**（用户全程未被问——S7-01 的直接证据）
- `current_step=reporting`，`degraded_nodes=[resource_scout, execution]`

即：import 错误反复修不好 → 烧光预算（92 次 LLM 调用，冲过 60 上限）→ 静默降级出报告 → 用户从头到尾没被问过一次。这一个 thread 同时坐实 S7-01、S7-02（4 轮全 import 修不好）、S7-03（烧过头）三点。

### 0.6 S7-03 根因：子上限只在轮边界检查，单轮内无法刹车

`MAX_DEV_LOOP_LLM_CALLS`（`config.py:112-114`，现值 60）声明是"修复循环子预算天花板"。但 `execution.py:2036` 的 `dev_calls < MAX_DEV_LOOP_LLM_CALLS` 判定发生在**轮边界**——即"进入下一轮修复回合前"才检查是否触顶。单轮 execution 内嵌 ReAct 子图一旦进入，就会一口气烧二三十次 LLM 调用（受 `REACT_MAX_ROUNDS_*` 约束但那是轮次不是调用），**中途没有任何刹车机制**。于是实测跑到 92（预期上限 60）、冲过头 32。

**翻倍治标不治本**：变更1 把 `MAX_DEV_LOOP_LLM_CALLS` 翻到 120 后，冲过头的绝对量可能更大（子图单轮烧的量不因上限翻倍而变），"轮边界才检查、单轮内无法刹车"这个机制问题原封不动。所以 S7-03 与"翻倍"是两件事：翻倍是给余量，S7-03 是修刹车粒度。

### 0.7 S7-02 根因：coder 修复反馈里全程看不到真实报错（信息链路 bug）

**坐实证据**（推翻 v0.1 "能力增强应等评测数据"的 backlog 理由）：模拟 coder 修复回合实际收到的反馈里——

1. `error_category` 只有一句笼统提示"import 错误（缺包/模块路径错误）"（`execution.py:1658` 一带的 `fix_hint=msg` 即这类笼统串）；
2. `stderr_tail` 取 logs 尾部 2000 字符（`execution.py:1121` `stderr_tail: _tail(logs)`），但**尾部恰是后续成功步骤的 stdout**——实测该 tail 里**不含** "No module named 'src'" 这个真正的报错行；
3. `representative_stderr=None`（`execution.py:1658-1659`、:2252-2253 均构造为空 `representative_stderr=""`）——代表性 stderr 片段根本没填。

三条叠加：**coder 全程看不到真实报错**。这不是 coder"能力弱修不好"，是系统把真报错在传给 coder 之前就丢了/截错了——**信息链路 bug**。checkpoints.db 中 `No module named 'src'` 出现 831 次，正是"看不到真错→每轮瞎修→同一个错反复出现"的直接后果。

**Maria 拍定方案**（写死为 S7-02 需求方向）：把"系统替 coder 决定看哪 2000 字"改成"给 coder 入口让它自主探索"——
- execution 每轮把**完整日志落盘成文件**（放 `code_output_dir` 下）；
- coder 修复反馈把截断的 `stderr_tail` 换成**日志文件路径** + 保留 `error_category` 快速提示；
- coder 用**现有 `read_code_file` 工具**自读完整日志、自主定位错误。
- 理念=最小改动（复用现有读文件工具，不新造观测管道），把截断决策权交还给 agent。日志落盘确切位置/是否需新工具/文件命名与轮次编号，交架构师（Q-S7-5）。

### 0.8 作品集 / 面试价值定位

本项目是 Maria 2026 秋招 agent 开发岗作品集（面试价值一等权重，观测性 / 人在回路 / 成本治理类价值高）。本治理族的讲点：**"修复循环失控"的系统性诊断与治理**——从"该问人时问人"（S7-01，HITL 升级点），到"想拦要拦得住"（S7-03，成本护栏的刹车粒度），到"给 agent 看真相而非替它截断"（S7-02，agent 上下文/工具自主探索的设计取舍）。这一族与 sp6 的 HITL 主题（不死锁/不失忆/不失联）一脉相承，补上"不失控"，并与 Sprint 7 成本追踪主题天然咬合（预算耗尽与子上限都是成本护栏的触发/刹车边界）。S7-02 的"日志文件路径换截断 stderr、让 coder 自读"是一个很好的 agent 设计取舍面试讲点（"别替 agent 决定看什么，给它入口"）。

### 2.2 S7-01 预算耗尽纳入 interrupt#2 人工升级（P0）

**背景 / 问题**（§0.3~0.5 已坐实）：`execution.py:2028-2030` 入口预算门在预算耗尽时直接 `return` 静默降级，绕过 interrupt#2。后果是"反复失败到山穷水尽"这个最该升级人工的场景，用户从不被问（实测 thread task-99eef17bccf2：4 轮 import 全败、92 次 LLM 调用烧光预算、`user_fix_decision=None`、直接出报告）。设计意图（interrupt#2 = 修复循环反复失败→问用户）与实际行为（预算耗尽→静默降级）南辕北辙。翻倍（§2.1）只是把掐断点推后，不改变"耗尽后静默降级"这个错误处置——所以翻倍**不替代**本条。

**需求描述**（行为契约）：

1. **预算耗尽（`budget < DEV_LOOP_MIN_CALLS_PER_ROUND`，翻倍后阈值为 4）不再静默降级**：该情形必须走**人工升级**，把决策权交还用户，而非替用户默认降级出报告。
2. **复用既有 interrupt#2 通道与两段式路径**：不新增 interrupt 种类（沿 sp6 "interrupt 种类集合不变"红线）。预算耗尽情形须经 commit-边界-return + self-loop-重入 的既有两段式抵达 `interrupt()`，不得在预算门处直接 `interrupt()`（保重跑幂等契约 S-1，见 §0.4、Q-S7-2）。
3. **决策面板须让用户感知"预算已耗尽"的终态语境**：面板文案须明确告知"修复已反复失败、重试预算已耗尽"，而非通用失败文案（沿 sp6 AC-S6-10 早停轮次上下文文案的既有做法——走既有 `summary`/`fix_hint` 通道喂 payload，零新 payload 键）。
4. **复用现有 interrupt#2 三态、不新增"追加预算"第四态**（Maria 反过度工程 + 预算已翻倍，见 §2.1 末、A-S7-1）：把"接受降级"映射到 export_code、"重来"映射到 revise_plan、"放弃"映射到 terminate。三态足以覆盖预算耗尽后的用户意图。
5. **成本硬约束不可破（对齐翻倍新值）**：`MAX_TOTAL_LLM_CALLS`（=240）/ `MAX_DEV_LOOP_LLM_CALLS`（=120）这类全局硬上限必须始终生效，绝不能突破硬顶。

**验收标准**：AC-S7-01 ~ AC-S7-04、AC-S7-06。

**非目标**（S7-01 不做）：

1. 不做"预算耗尽降级"与"其它原因降级"的差异化报告标注体系——沿用既有降级声明链路（sp5 S5-01/S5-04 通道）。
2. 不改预算的计量算法（口径不变），只改"耗尽后的处置"与"额度大小"（翻倍）。
3. 不做撤销/改主意通道——沿 sp6 非目标 4，一次决策即生效。
4. 不加"追加预算"第四态（Maria 已明确不加）。

### 2.3 S7-02 修复循环 coder 看得到真报错（P1）

**背景 / 问题**（§0.7 已坐实为信息链路 bug）：coder 修复回合实际收到的反馈里，`error_category` 只有笼统一句、`stderr_tail` 取到的是后续成功步骤 stdout（不含真报错行）、`representative_stderr=None`——coder 全程看不到真实报错，反复瞎修（`No module named 'src'` 出现 831 次）。这是系统在传给 coder 前就把真报错丢了，非 coder 能力问题。

**需求描述**（Maria 拍定方案，最小改动）：

1. **execution 每轮把完整日志落盘成文件**，放 `code_output_dir` 下（确切路径/命名/轮次编号交架构师 Q-S7-5）。

4. 理念红线：**把"系统替 coder 决定看哪 2000 字"改成"给 coder 入口让它自主探索"**——这是本条的设计取舍本质，实现不得倒退回"系统再挑一段塞给 coder"。

**验收标准**：AC-S7-05、AC-S7-07。

**非目标**（S7-02 不做）：
1. 不改 coder 的修复策略/prompt 结构本身（最小化编辑 vs 整份重生成不在本条范围）——本条只保证 coder"看得到真相"，看到之后怎么修是既有能力。

3. 不动决策面板给用户看的 stdout 尾部（那是 sp6 MF-7 的人向链路，与本条 agent 向链路正交，两者互不改动）。

### 2.4 S7-03 修复子上限拦得住（P1）

**背景 / 问题**（§0.6 已坐实为机制层缺陷）：`MAX_DEV_LOOP_LLM_CALLS` 子上限只在**轮边界**检查（`execution.py:2036`），单轮 ReAct 子图内部一口气烧二三十次调用无中途刹车 → 实测冲到 92、超上限 60 达 32。翻倍到 120 后机制问题不变（治标不治本）。

**需求描述**（行为契约，不预设实现）：

1. **修复子上限须能在单轮 ReAct 子图内部生效**，而非只在轮边界——当 `_dev_loop_llm_calls` 逼近 `MAX_DEV_LOOP_LLM_CALLS` 时，子图应能及时停止继续烧，冲过头的幅度须被约束在一个确定性小范围内（可接受的越界上界交架构师定，Q-S7-6）。
2. **刹车触发后走既有升级/降级路径**，不新增 interrupt 种类：子上限触顶本就是 interrupt#2 的既有触发原因之一（`execution.py:2077` "子预算触顶"），本条只保证"触顶被及时发现"，触顶后的处置沿用既有。
3. **不改计量口径**：`_dev_loop_llm_calls` 怎么累加不变，只补"逼近上限时的刹车检查点"。
4. 与翻倍解耦：翻倍是 §2.1 的额度调整，本条是刹车粒度修复，两者独立验收（翻倍后仍须验证 S7-03 的刹车生效）。

**验收标准**：AC-S7-08。

**非目标**（S7-03 不做）：
1. 不追求"精确不越界一次不差"——ReAct 子图内检查点有天然粒度，产品要求是"约束在确定性小范围内"，不是"零越界"（避免过度工程做逐调用拦截）。
2. 不改 `REACT_MAX_ROUNDS_*` 轮次上限语义（那是轮次不是调用数，正交）。

### 2.5 S7-05 修复循环记忆增强（P1，方案待架构）

**需求**：coding↔execution 修复循环里，coder 每个修复回合从 fresh messages 起步，看不到自己前几轮试过什么，极可能反复套用同一种无效改法（现场 thread task-99eef17bccf2 实测 4 轮全栽在 import）。给 coder 补上"跨回合记忆"，使它能从"上轮改了什么、结果如何"里学习、做增量修复决策，而非每轮当新病人从头问诊。

**缺口坐实（源码级）**：
- `react_base.py:49` `ReActState.messages` 与 GlobalState **完全隔离**；coder 每修复回合从稳定 SystemMessage + curated HumanMessage（`_build_coding_context`，coding.py:301）重新构造，子图内 messages 结束即丢、不回写 GlobalState。
- `fix_loop_history`（`state.py:176` 结构完整、`execution.py:2167` 每轮 `_append_fix_record` 写入）**已维护但从未注入 coder**——`_build_coding_context` 全程没引用它。
- 且其字段（error_summary/error_category/fix_strategy）是 `_classify_execution`（execution.py:215-351）的**规则模板文案**（匹配 stderr 关键词套预设描述，零 LLM），信息粗——这正是 Maria 否决"只注入这些摘要"的原因（太模糊）。

**Maria 决策（v0.4，要"两极之间"的中间方案）**：
- 否决**档 A「只注入 fix_loop_history 规则摘要」**——信息太粗太模糊，coder 看了只知"又是 import"、不知"上轮具体改了啥、为啥没成"。
- 否决**档 C「完整对话 + 工具调用结果全塞」**——会撑爆 context（长度随回合线性增长、逼近 token 上限）。
- **要架构师设计档 B：一套信息比规则标签丰富、又控量不爆的记忆机制。**

**与 S7-02 边界**：S7-02 治"当前轮真报错可见"（空间维度，已交付），S7-05 治"历史尝试记忆"（时间维度）。正交不重复。

**技术约束（给架构师，已澄清、勿推翻）**：
- **Prompt Cache 非障碍**（Maria 校正）：GPT-5.4/OpenAI 是 token 级自动前缀缓存，历史放**整个 prompt 的动态尾部**（稳定前缀之后）前缀照常命中、只有历史段 miss（正常增量）。不采用任何"塞历史破坏 cache"的理由。
- **sort_keys 坑**：当前 curated payload 走 `json.dumps(sort_keys=True)`（coding.py:347），新增历史字段会按字母序插中间、打乱前缀字节——要让历史落尾部得绕开 sort_keys 块。
- **context 长度要控**：这是"档 B 而非档 C"的核心动因，架构方案须给出显式控量机制。

**架构须回答（方案设计要点，留架构师）**：
1. **每轮记什么**——比规则标签丰富（如 coder 上轮关键动作/代码 diff 摘要 + execution 上轮真错关键行），又比全对话省。信息选取的粒度与来源？
2. **怎么控量**——滚动窗口（最近 K 轮）/ 只留关键轮 / 结构化压缩表示；是否引入比规则模板更丰富的每轮摘要（若要 LLM 二次摘要须评估成本，Maria 反过度工程）。
3. **放哪**——动态尾部避 sort_keys 的具体落法（承接原拟 Sprint 8 的 sort_keys 问题）。
4. **跨 agent 范围**——只给 coder 自己的历史，还是也把 execution agent 的关键信息纳入。
5. **是否触碰子图隔离**——档 A 只往 HumanMessage 注数据不破隔离；若档 B 要 coder 看到自己历轮真实推理，是否需回写子图 messages（破隔离）——权衡代价。

**验收标准**：AC-S7-09~14（见 architecture v1.1 §13.8；AC-S7-11/12 须逐环验红防"coder 说了但没进历史"假绿）；须遵循"注入生效可观测、非假绿"与现有 coding context 回归零退化。

**架构方案已定**（`docs/sprint7/architecture.md` v1.1 §13，Maria 二轮修订）：每轮**五元组** round/category/files_touched/**fix_note（coder 在 `<result>` 顺带自述"本轮问题定位+修复逻辑"）**/log_path，**全部记录保留无窗口**（MAX_FIX_LOOP_COUNT=20 + fix_note 120 字双封顶控量）；渲染成单键 `fix_history_digest` 塞 curated context 尾部（sort_keys 只排顶层键）；链路 coder→`_map_coding_result` 写 `last_fix_note`→下轮 `_append_fix_record` 取（时序天然对齐）；只给 coder、不破子图隔离、不加 LLM、不加 execution 判定理由。state +4 键旧 checkpoint 兼容。

**非目标**：不做"历史无脑全量堆积"（撑爆）；不与 S7-02 当前轮日志链路重复。

### 2.6 S7-06 资源探索能实际探测本机环境（P1，护栏方案待架构）

**需求来源与教训**：Maria 在 Sprint 7 真人端到端复验中提出——资源探索环节只读论文、只搜网页，对"这台机器到底是什么样"一无所知，只能靠猜。此诉求 Maria **两次复验都提过**：第一次仅在对话里口头应了一声、**未落进 TODO / PRD / 记忆任何一处** → 没进需求池 → 漏做；第二次复验发现仍未做，才当场固化为 TODO `[E2E-2 发现②]`。**根因是需求固化流程漏，不是技术不可行**——这条教训本身已写进 TODO 的防蒸发区块。Maria 本轮同时**更正了诉求对象：是资源探索节点，不是计划制定节点**（TODO 曾一度误记为后者）。2026-07-27 Maria 决定不新开 PRD、并入本 PRD（§4.1）。

**问题**：当前资源探索的判断输入只有两类——论文里写了什么、网页上搜到什么。于是它给出的"用这个仓库 / 部分复用 / 从零实现"结论，以及下游复现计划所依赖的资源前提，**全部建立在对本机环境的假设之上**：有没有 GPU、显存多大、CUDA 与驱动什么版本、常用依赖是否已装、磁盘还剩多少。这些事实**在本机上一条命令就能问出来**，系统却选择去猜。后果是资源结论与真实执行环境脱节，代价要到下游才暴露（装不上 / 跑不动 / 显存不够），而那时预算已经烧掉大半。

**现状坐实（源码级，已逐条核实）**：

1. `core/nodes/resource_scout.py:571-577` 工具集恰 **5 个**（`web_search` / `search_papers` / `get_paper_brief` / `git_clone_and_analyze` / `check_url_reachable`），**无任何运行命令能力**；`core/nodes/planning.py:719-725` 同样没有。
2. `core/tools/run_command_tool.py` **已存在且护栏齐备、可复用**：禁 shell（`shlex` 解析为 argv，管道 / 重定向 / `&&` 天然不可用）、进程组隔离、超时杀子树（`RUN_COMMAND_TIMEOUT=120s`）、输出字节截断、`mask_value` 脱敏、失败一律转结构化 JSON 不抛异常炸子图。

**安全边界（产品红线，本需求的核心产品问题）**：

让 agent 在宿主机上跑命令有真实风险。**"只读"这条线必须由机制强制保证，不能只写在 prompt 里靠模型自觉**——模型不服从是常态，本 sprint S7-05 真跑实测 coder 输出约定遵守率仅 **75%**（3/4），即为实证。prompt 约束不构成保证。

**【2026-07-28 补：这条红线的适用面，防两个方向的误读】**"必须机制强制"约束的是**只读 / 安全边界**——越界后果不可逆（装了、删了、下载了、私有数据被读了），故不接受任何靠模型自觉的方案。**它不覆盖"探几条"这类量控**：量控的失控代价可逆（多花几轮预算），且已有确定性机制兜底（节点轮次硬顶 20，`react_base.py:621-629`，探测再放飞也突不破），故 Q-S7-12 裁为**只做 prompt 措辞、不加机制计数器**，并以 AC-S7-25 作可证伪出口（真机观测 > 5 条即为"措辞不够"的实证，届时才加计数器）。**两个方向都要防**：①拿本红线去要求给"探几条"造计数器 = 为尚未观测到的问题预造机制（反过度工程）；②拿 Q-S7-12 的 prompt-only 先例去松动只读边界 = 把不可逆风险交给 75% 的遵守率。

**允许探测**（说人话的类别，不是要求实现成枚举）：
- 硬件与驱动：有没有 GPU、显存多大、驱动与 CUDA 版本；
- Python 环境：解释器版本、已安装的包及版本；
- 基础工具链：git、编译器等是否可用及版本；
- 磁盘可用空间（决定数据集 / 权重能不能落地）。

**禁止**（须机制性拒绝，不是靠提示词劝阻）：
1. **任何改变机器状态的动作**——安装、卸载、删除、覆盖写、改配置、改环境变量持久化；
2. **任何联网拉取 / 下载**——检索是网页搜索工具的职责，探测就只是探测；
3. **读取与复现无关的用户私有数据**——家目录文件内容、凭证文件、shell 历史等。**"只读"不等于"无害"，隐私边界必须一并划进来**；
4. **长耗时 / 重负载**——跑训练、跑基准测试属执行阶段职责；
5. **借通用解释器执行任意代码**——如 `python -c "..."` 这类，会让任何基于命令名的限制形同虚设。产品判断：**探测需要的是"查"，不需要"跑任意代码"**，所以这个口子直接不开。这也是与 coding 阶段 smoke 自查用途的**关键分野**——那边正需要 `python -c` / `py_compile`，两个用途的边界不同，不可混为一谈。

**其它边界**：

6. **不引入人在回路确认**：不新增中断种类（沿本 PRD 既有红线），不为每条探测命令弹窗打断用户。理由=只读边界一旦由机制保证，风险已收敛；且逐条确认会把"省得靠猜"的收益抵消殆尽。此为**可单点推翻**的产品判断（A-S7-9）。
7. **拒绝行为**：命中禁止边界时返回**结构化拒绝**、让 agent 换招继续，不抛异常炸子图、不导致节点整体失败（沿现有工具的错误处理范式）。
8. **不得回归 coding 现有行为**：`run_command_tool.py` 是 coding smoke 在用的**共享工具**，为本需求所做的任何改动必须对 coding 侧**零影响**。

## 4. 需求裁决说明（v0.1 → v0.5 的范围变化）

v0.1 曾把附A/附B 列 backlog，理由是"能力增强、应由评测数据驱动"。**v0.2 起推翻此裁决并经 v0.3 收敛**，理由如下：

- **附A → S7-02（转正 P1）**：坐实证据（§0.7）表明它不是"能力增强/效果优化"，而是**信息链路 bug**——coder 根本看不到真报错。bug 不需要评测数据驱动、可直接确定性修复（构造 import 现场即可验证），backlog 理由（缺度量基线）不成立。且 Maria 已拍定最小改动方案（复用 `read_code_file`，不新造管道），量级可控、不稀释 P0。
- **附B：Maria 决定不做（完全砍掉、不进 backlog）**：S7-02 已让 coder 在 execution 报错后自读完整日志、自主定位 import 错误，"生成后进 sandbox 前再加一道 import 预检"在 S7-02 之上属多余——直接砍掉避免过度工程（符合 Maria 反过度工程一贯原则）。此项不再作为需求、不作为 backlog、不再出现在本 PRD 后续任何章节。
- **新增 S7-03（P1）**：实测烧 92 超 60 上限 32，是**机制层缺陷**（刹车粒度错），有直接现场证据、不依赖评测数据，与预算翻倍解耦（翻倍治标不治本）。纳入本治理族而非另起 PRD，因它与 S7-01 共享"修复循环失控"的成本护栏语境。

## 9.1 需求背景（实证驱动，非拍脑袋）

1. **定位问题**：探测段落标题写的是「**可选补充步，不属于上面的优先级链**」。agent 是完成任务导向的——走完三步优先级链即交卷（实测仅 3 轮：`check_url_reachable_tool` → `git_clone_and_analyze` → 输出 `<result>`），**链外可选项自然不碰**。

## 10.2 目标与非目标

### 目标

1. **本机优先**：本机能完整复现且对本机无负面影响时，计划就按本机实际情况写、按本机真跑。
2. **事实优先于推断**：本机实测 > 论文推断 > 明确写"未探测/未知"，三级优先级由 prompt 契约确立。
3. **禁编造**：探测未覆盖的维度**不得给具体数值**（内存那条就是反面样本）。
4. **不够就当场问**：本机不够时，把两个选项摆到用户面前——(a) 缩小规模仍在本机真跑；(b) 只产代码不执行。
5. **缩规模必须诚实**：走 (a) 的复现必须全链路贯穿并在报告强制声明，且**不得评为科学复现**（Maria 2026-07-29 裁定）。

1. **远程/云服务器执行不做**（Maria 2026-07-29 裁定）。询问用户时**不出现"提供其他远程机器"选项**。依据：`core/state.py:365` `sandbox_type` 写死 `"venv"`，无远程底座；与全局文档 §7.2「云服务器远程执行 → v2」一致。
2. **不加任何硬性 gate / 确定性拦截门**（Maria 原话「这种不是需要你硬性 gate 的问题」）。不扩 `core/plan_checks.py`。
3. **不做"计划与实测偏离"的留痕**（Maria 2026-07-29 追加裁定：**连留痕也不要**）。偏离一律靠 §10.6 的审核页披露交由人眼判断，系统不产出任何机器可读的偏离信号。原 Q-S7-16 据此**撤销**。
4. **探测清单放开（命令名白名单 + 参数校验）剥离为独立需求 S7-09**（Maria 2026-07-29 裁定），不阻塞本需求。**关键依据**：本次需要的 6 项必探维度**全部已在现有 15 条清单内**（`core/tools/env_probe_tool.py:75-82`，主控 2026-07-29 逐条核实属实），缺的只是 prompt 没让它探——本需求只改提示词，`env_probe_tool.py` 零改动。

## 10.4 核心场景（三分支 + 一兜底）

### 场景 A：本机够，且对本机无负面影响

- 规划按论文规模写；`environment` 章节的 GPU / 内存 / 磁盘 / Python 一律**以本机实测为准**，探测没覆盖的维度写"未探测"。
- 计划自带一段中文的**本机适配说明**：这台机器实测到什么、能不能完整跑、本次预计占用（GPU 张数 / 显存 / 磁盘增量 / 预计时长）。
- 用户在审核页看到说明后批准 → 正常执行。**零返工。**

### 场景 B：本机不够

- **规划首轮产出的就是"这台机器跑得动的版本"**，不是"先出理想计划、用户选降级后再重写"。计划里显式写清：缺口是什么（缺 GPU / 显存不足 / 磁盘不够 / 缺关键依赖）、按什么方式缩的（如更小的模型、数据子集、减少实验组）。
- 审核页把两个选项摆给用户，**映射到面板上已有的两个按钮**：
  - (a) 接受这个缩规模版本、在本机真跑 → 批准；
  - (b) 不接受缩规模、只要代码不执行 → 仅生成代码。
- 用户想换一种缩法（"别减实验组，改减数据量"）→ 走审核页已有的对话式修改（`ui/pages/plan_review.py:548-592`），属**可选精修**，非主路径。
- 批准后：缩规模标记全链路贯穿到编码与执行（防下游"好心"改回论文原始规模）；报告**强制声明**且**不得评为科学复现**。

### 场景 C：本机跑得动，但对本机有负面影响（占满 / 满载数天）

**Maria 2026-07-29 裁定：系统只披露、不判、不自动降级。**

- 理由：这台机器是不是共享机、别人在不在用、能忍受占用多久，**是用户偏好而非机器事实，探测永远探不到**。
- 系统做的是**披露**：把预计占用（GPU 张数 / 显存 / 磁盘增量 / 预计时长）连同 `estimated_time` 一并呈到审核页，由用户按按钮。
- 用户可：批准照跑 / 要求缩到可接受的占用（走精修）/ 只要代码。
- **不设任何占用阈值、不做自动降级触发**。

### 兜底场景 D：本机事实缺席（探测全失败 / 未探到）

- `local_env_facts` 为空 ⇒ 规划上下文里**该键不存在**（S7-06 既定语义，不造哨兵值）。
- 此时计划**必须显式写"未探测 / 未知"，禁止凭常识补具体数值**——这正是本次内存那条的反面要求。
- 不阻断、不降级、不标记节点降级（沿 AC-S7-17 精神）。

## 10.5 "本机够不够"由谁判定、判定输入是什么

**判定人 = 规划节点的模型（LLM），在生成计划时一并判定并写进计划。不做确定性规则判定。**

三条理由：

1. Maria 已否掉硬性 gate、并进一步否掉留痕 ⇒ 确定性判定**没有任何消费方**，投入产出比极差。
2. 做确定性判定要求推翻 S7-06「最小单键 `str`」裁决（`core/state.py:290-296`），并为 `nvidia-smi` / `lscpu` / `free -h` / `df -h` 四种异构文本各写脆弱正则——典型过度工程。
3. **决定性理由：确定性规则拿不到分子。**"够不够" = 需求 ÷ 供给。供给（本机事实）在 state 里；**需求（模型参数量、数据集体积、训练步数、实验组数）只存在于论文语义与计划草案里，没有任何结构化字段承载**。规则算不出这个商。

**判定输入（三项，缺一不可）**：
1. 本机实测事实 `local_env_facts`（已在上下文，`planning.py:355-358`）；
2. 论文侧硬件推断 `hardware_requirements`（已在上下文，`planning.py:296-299` 白名单内）——**优先级低于 1**，且可能缺失；
3. 计划草案自身的规模含义（模型 / 数据 / 实验组 / 步数），由模型自行从论文语义得出。

**判定结论的落点**：写进复现计划的**一个新子键**，采**两键极简形态**（主控按最小设计裁定）：是否缩了规模（机器可判信号）+ 一段通俗中文说明（够不够、缺口、预计占用）。缺省安全值 + 下游一律防御读（旧 checkpoint 兼容）。**不加"够不够"与"缺口清单"独立键**——审核页本就恒常展示说明，条件分支不必要。

**缩规模的"度"**：由模型自行决定缩多少，用户可走精修调整（主控按最小设计裁定）。**不做固定档位枚举**（1/10 数据 / 单实验组 / 小模型）——不同论文可缩维度差异大，固定档位适配性差且属新增枚举。

**"对本机无负面影响"这一维度**：系统**不判、只披露**（见场景 C）。现有探测的覆盖情况——GPU 占用进程/显存（`nvidia-smi` 裸命令即输出，清单内）、内存（`free -h`，清单内但没被探）、磁盘（已探）可覆盖；**数据集体积只能由模型从论文估**；**"是不是共享机 / 能忍多久"永远探不到**。

## 10.6 询问用户的时机与文案要点

### 时机：随现有计划审核中断一并问，不新增中断、不新增按钮

- **时机点 = 计划产出之后、用户审核之时**（复用 `core/nodes/planning.py:877-891` 的 `interrupt_kind: "planning"`）。
- **为什么不能放在规划之前**："够不够"依赖计划内容——规划之前只有本机事实（分母），没有"要跑多大"（分子），算不出商；那时问用户等于让她盲选。
- **为什么不返工**：因为场景 B 的计划**首轮就是本机版**，用户按下的两个按钮都不触发重写。
- 决策类型集合**保持既有 5 类**（批准 / 仅生成代码 / 修改 / 换仓库 / 取消），**不新增第 6 类**。

### 审核页要展示什么（新增一个只读展示块，恒常展示而非条件隐藏）

1. **这台机器实测到什么**——本机实测事实原文只读展示（当前用户完全看不到它，这是本次 bug 无人察觉的根因之一）；
2. **按这台机器能不能完整跑**——够 / 不够 + 缺口是什么；
3. **本次预计占用**——GPU 张数 / 显存 / 磁盘增量 / 预计时长（场景 C 的披露载体）；
4. 若走了缩规模：**缩了什么、怎么缩的**。

> 注：现状 `environment` 只以**默认折叠的原始 JSON** 呈现（`ui/pages/plan_review.py:290-293`），不足以承载上述内容——本次不得把说明只塞进那个折叠块了事。

### 文案要点（面向用户，红线）

- **一律通俗中文**；禁止出现任何内部枚举值、字段名、节点名、工具名、自创英文缩写。
- **不得出现"提供其他远程机器"或任何暗示远程执行的选项**（本次明确不做）。
- 探测未覆盖的维度，文案写"**未探测**"，**不写数字、不写"建议 XX GB"**。
- "仅生成代码"按钮在**本机不够**的情境下，需补一句上下文说明（大意：这台机器跑不动，可以只产出代码、之后拿到机器再跑），**不改按钮本身、不新增按钮**。
- ⚠️ **守门盲区须一并处置**：现有术语守门 `tests/test_e2e2_message_guard.py:27` 的 `_GUARDED_MODULES` **仅含 `resource_scout`**（主控核实属实），planning / reporting / UI 的新增文案**当前无人守**。S7-06 恰因"守门范围指错、扫到 0 条却 passed"吃过亏，本次不得重蹈（处置方式见 Q-S7-14）。
