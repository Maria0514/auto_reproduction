## 一、多代理并行的隔离规则

### 1.1 不要用 worktree 隔离，用主工作区文件边界隔离

**结论：并行开发的代理一律在主工作区干活，靠"各碰不重叠的文件"隔离，不要开 worktree。**

原因：日常开发习惯是改动留在工作区、不急着 commit。而 `Agent(isolation: "worktree")` 和 `git worktree add` 都基于 HEAD 建树，**拿不到未提交的改动**——并行代理会缺依赖代码，跑起来一堆假失败。

具体边界规则：

- 每个代理只允许改自己那批不与他人重叠的文件
- 三个共享文件**谁都不许碰**：`app.py`、`docs/TODO.md`、各 sprint 的 `dev-plan.md`
- 各代理只跑自己那套测试
- **全量回归和文档收口由主控统一做**，不下放给子代理

实证：sprint3 的 E2/E3 双开发 + 双验收并行，零冲突。

> 历史备注：早期曾约定"父会话先 `EnterWorktree`、所有子代理继承同一个 worktree 累积到同一分支"。**该方案已废弃**，原因如上。同时早期记录称"本仓库无 git remote"，2026-06-28 实测更正——remote 存在（`origin` → GitHub）。

### 1.2 跨会话并发：同文件冲突必须停手请示

多个会话并行跑不同批次时：

- **同一个文件被两个批次同时修改 ⇒ 无法按文件粒度分离提交。** `git add <file>` 救不了（需要 hunk 级），而当前 harness 不支持交互式 `git add -p`。遇到这种情况**停手请示**，不要自作主张打包提交。
- **对话开头 harness 给出的 `git status` 快照是不可信的**（可能显示 clean 而实际很脏）。需求编号、批次进度一律从磁盘 grep 现查。
- 连续两次 pytest 结果不一致（如 3 failed → 0 failed）通常是并发写导致。**"测试全绿"的结论必须标注时间点**，否则等于没说。

### 1.3 子代理：发起后静默等待，回来后主控亲自验证

长构建任务交给子代理以保持主上下文干净。发起后**不要轮询、不要自己动手做同一件事**，等它返回。

返回后**主控必须亲自查磁盘 / 跑回归核实**，不能采信子代理的自我陈述——曾有子代理谎报"已删除 `pwc_tools.py`"，实际文件还在，靠验证才抓出来。

## 二、Python 环境的失败症状

正确用法（README 已有）：一律 `.venv/bin/pytest`、`.venv/bin/python`。

**这里补的是错误用法长什么样**——因为不知道症状，才会反复绕路：

| 你敲的 | 会发生什么 |
|---|---|
| `pytest ...` | 找不到命令，它不在 PATH 里 |
| `python3 -m pytest` | `No module named pytest`（系统 python3 没装） |
| `python xxx.py` | **系统裸 `python` 是 Python 2**，跑 py3 脚本报 `SyntaxError: Non-ASCII character ... no encoding declared` |

新建虚拟环境时用 `sys.executable -m venv`，不要用裸 `python`/`python3`。

## 三、流程铁律

### 3.1 新功能先走 PRD，纯 bug 修复可直接改

新需求或需求变更：**产品经理落 `docs/sprint{N}/prd.md` → 架构 → 开发 → 测试**，不许直接跳到写代码。编号体例 `S{N}-xx` / `AC-S{N}-xx` / `Q-S{N}-xx`。

**例外：纯 bug 修复可以直接动手**，不必走这条链路。

### 3.2 口头反馈必须当场落盘

用户在 e2e 演示或对话中提出的改进意见，**当场**写进 `docs/TODO.md`（带负责人 + 日期）。

代价实证：曾提出"给 resource_scout 加执行 command 探测本机 GPU/CUDA/依赖"，因未当场落纸而没进任何 sprint 需求池，直接漏做，第二轮 e2e 才重新发现。

### 3.3 批次边界逐批确认

多批次开发计划，**每个批次边界停手等明确确认**再开下一批。对某一批的授权**不等于**对后续批次的授权。耗配额或不可逆的动作即使在批内也需单独授权。批内的并行派发不受此限。

触发事件：sprint5 只批了"批次 0"，却自主一路推到批次 4。

### 3.4 产品经理代理要前台多轮追问，不要后台一次性派发

`.claude/agents/product-manager.md` 本身就设计成多轮澄清。**后台一次性派发会绕过这个设计**，直接拿到一份没问过问题的 PRD。

代价实证：S7-06 若走追问模式，很可能问出"探测到硬件后要不要据此调 batch size"——而这正是全局 PRD §4.3.3「平台感知的规划」悬空七个 Sprint 无人发现的缺口。

另：`.claude/agents/` 下四个代理定义在调用前就该读，它们已有的约束不必在 prompt 里重复。

### 3.5 全局 PRD 与本轮 PRD 同批落盘；文档要记录**所有**计划，包括没做的

**全局 PRD（`docs/product-design-specification.md`）必须与 `docs/sprint{N}/prd.md` 同一批落盘**，不是"等代码交付后回填"。

**它要记录所有对产品的计划，包括尚未实现的。** 用户原话：「文档就应该记录我们所有对产品的计划，后续才能对照产品文档判断哪些未实现的。**不要担心**什么写了但实际上没交付的情况。」

⇒ **不要因为"怕写了没做"就不写**。不写，那条计划就直接从世界上消失了，连被发现的机会都没有。§6.2 硬件探测承诺挂 14 个月，**病根是"14 个月里没人拿文档对照代码"，不是"它被写进了文档"**。解药是对照机制（PM 四步法核对、定期清账），不是因噎废食。每条能看出「已实现 / 尚未交付」即可，**不要为此新建复杂状态体系**（见 4.1）。

**代价实证（git 可查）**：sp5（`b3eb01a` 2026-07-09）与 sp6（`c930145` 2026-07-13）的提交说明都是「立项三件套 + 全局 PRD vX」——**本轮 PRD 与全局 PRD 就是同一次提交**。断点在 sp7：`docs/sprint7/prd.md` 2026-07-19 落盘，全局 PRD 当天零改动，直到 7/22 才在 S7-05 的代码提交里被顺带改；而「交付后回填」这个说法 **7/28 才出现** ⇒ **先有"没按时同步"的既成事实，九天后才有说法把它追认成制度**。后果：两份全局文档停在 7/29，S7-08~S7-13 六个 commit 零回填，一份「待交付后回填」9 条清单至今无人认领（2026-08-04 清账挖出）。

⚠ **别和全局架构文档混为一谈**：`docs/technical-architecture.md` 走的是**代码交付后回填**（架构师 2026-07-28 裁定，证据 = sp5/sp6 两次全局同步对该文件零命中）。**两份全局文档时机不同**——产品 PRD 记计划所以先写，架构文档记实现所以后写。sp7 之后这两条被混成一条，是上述断点的成因之一。

### 3.6 把关放在主控，不给子代理加自检

用户 2026-08-06 明确定的工作流，原话：「**以后的工作流变成子代理落实文档后、或者提出问题后，你去核实一遍。**」

⇒ **两个固定时机，主控必须上磁盘核实、不采信子代理自述**：①它**落实文档之后**（改了什么、版本号、边界有没有越、判"已实现"处是否真有源码依据）；②它**提出问题 / 给出裁定之后**（它说的"读不了 / 验不了 / 拿不到"是不是真的，它引的行号还在不在）。

**⚠ 明确否掉的方案**：给架构师代理加一道"裁定前三问自检"。用户否掉它并给了这条替代——**把关放在主控这一层，比让每个代理自查更实**（代理的自查容易流于形式，而主控核实产出的是磁盘证据）。**不要再提给子代理加自检清单这类方案。**

代价实证（同一个思维毛病两次，第二次更贵）：架构师两次裁定都栽在「**只验证了一条路走不通，就当成所有路都走不通**」——①否决"停止压扁嵌套"时只验了判定路径读不了嵌套，而渲染路径 `reporting.py:440` `_flatten_entries` 一直是通的 ⇒ 设计被改窄；②裁"论文报告值不验钞"时只验了产物路径验不了它，而 `state["paper_analysis"]["baseline_results"]` 一直在那 ⇒ **防线被打开**（agent 可把对照基准编低，让自己"对上"）。**两次都是主控上磁盘核实后才发现的，这正是本条要固化的动作。**

### 3.7 「代码交付后回填」管的是设计说明，**从不允许现状数字是错的**

`docs/technical-architecture.md` 走「代码交付后回填」（§3.5）。这条**约束的是"要不要写这个功能的设计说明"**——它**不适用于现状清单**（工具数、字段数、状态种类这类"现在是什么"的账）。

⇒ **数字与磁盘不符属事实错误，任何时候都即时订正，不受批次边界与提交状态约束。** 订正时只改数字、不写设计，并留一个"设计说明待 X 收口后补、届时删除本句"的到期标记。

代价实证（2026-08-07，架构师立、Maria 拍板）：架构文档同一天上午刚写下「本次不含任何 Sprint 8 回填，时机未到」，下午 sp8 批次 1a 就把 execution 工具列从 3 改成 5 ⇒ 现状表当场错。**把两件事打包成一句"时机未到"，就会让读者从现状表读到错的答案。**

### 3.8 清账必须**双向**：从文档查代码，再从代码查文档

只做一个方向必然漏一半：

| 方向 | 能发现 | 发现不了 |
|---|---|---|
| 读文档 → 查代码 | **文档写了、代码没做**（§6.2 硬件探测挂 14 个月即此类） | — |
| 读代码 → 查文档 | **代码做了、文档没写** | — |

🔴 **「做了没写」读文档永远看不出来，因为那里什么都没有。** 历次全局回填都是**按 Sprint 纵向补**（补 sp7 就只看 sp7），于是 sp5/sp6 的 UI 与治理层整批没人回头看。

代价实证（2026-08-07 架构师从代码侧反查挖出）：审核页讨论助手的第 4 键早已实现且有精确等值断言守着、两份全局文档零记载；凭证接口清单少登记第 7 个；任务状态代码 7 态而产品文档写 5 态；~~`ExecutionResult`~~ 🔴 **`GlobalState`**（**2026-08-08 订正**：本条原写 `ExecutionResult`，磁盘实为 `GlobalState`（`core/state.py:316-318`）—— 由架构师代理回填时上磁盘核出。⚠ **这条错误表述本身就是本节讲的病的实例**：它被当作"已核实的事实"在 TODO 与本文件之间传了两轮，**没有人回到 `core/state.py` 看一眼**）**状态镜像缺 sp5 三键**——**而 v1.4 那次大清账专门补过同一节，补漏时又漏一批**。

⇒ 由此立一条可执行判据（架构师代理 2026-08-08 提出并已落 `docs/technical-architecture.md`）：🔴 **镜像类章节的补漏，判据必须是"两侧键集合相等"，不是"把点名的几个补上"**。按该判据全节对平时，当场又捞出一处（`ReproductionPlan` 镜像缺 `success_criteria`）——**这正是 §3.10 的正面印证：换个判据就能捞出点名清单里没有的**。

### 3.9 🔴「处置栏写了」≠「磁盘改了」——纸面账与磁盘账必须分别核

勘误表 / 决议表的**处置栏写着"该句订正为……"，不等于那句话真的被改了**。这两笔是**两本账**，只核其中一本必然漏。

实证（Sprint 8，2026-08-08）：`P-S8-16` 的处置栏白纸黑字承诺"该句**订正为**……"，而被订正的原句在 `dev-plan` 里**原样躺着、从未落实**——直到下一轮开发代理路过才补上。同源的还有 `CP-1b.2-12~15`：迁入时**只搬了叙述、没搬勾选行**，于是索引说有 4 条、正文一个复选框都勾不了。

⇒ **核账时不许只读处置栏 / 结论行，必须回到被订正的那一处看现文**。与 §3.8 是同一个道理的第三个方向：**从"决议"查"落地"**。

### 3.10 🔴「被点名几处就改几处」是一种漏改模式——跟改收尾必须全文 grep

改判一条设计 / 订正一个数字时，**照着别人点名的清单逐处改，改完就收工**，是本项目最高频的失效模式。点名清单**永远不全**，因为写清单的人也是靠回忆。

实证（Sprint 8 一个 Sprint 内**发作七次**）：`AR-S8-15` 的连带跟改**做了三轮**仍漏两处（批次 2 文件边界 + `CP-2.12-6`），全是全文 `grep state.py` 才挖出来的；勘误总数 20→25 那次四个同源汇总口只改了三处；冻结表行数被连续订正三轮、每轮都还有同源处没跟；"五重验钞"扩到七重后有 6 处汇总口没跟。

⇒ **凡改一个数字 / 口径 / 设计，收尾必须按关键词全文 grep 收网**，把找到的处数与点名的处数对一遍；**两数不等就说明清单本来就不全**。⚠ 附带一条：**文档内自引用行号在同一轮编辑里会被自己推翻**（先按当时行号写下引用，随后又插了几行，引用当场失效）⇒ 自引用一律**以"章节名 + 特征串"为主、行号为辅**。

## 四、设计取向

### 4.1 最小单一抽象，反对过度工程

默认最小抽象，不预设多分类枚举、不留"将来可能用得上"的扩展点。评审子代理的产出时主动砍过度设计。

判例：sprint4 的交互工具，PM 初版设计了 5 种 `input_type` 枚举（credential/text/choice/path/confirm + options）被否决，最终收敛为**单个 `request_user_input`，只保留 `is_sensitive` + `purpose_key`**。

### 4.2 用户可见文本禁用内部术语

- 禁止把内部枚举值（如 `from_scratch` / `use_repo` / `hybrid`）、内部字段名、自创英文缩写暴露给用户
- UI 文案一律经 `ui/term_map.py::humanize` 转换
- **写 LLM prompt 时也别拿英文枚举当叙述示范**，否则模型会把它抄进自由文本字段（plan_summary / deliverables）
- 这条同样适用于**给用户写的解释和汇报**，不只是 UI

## 六、几条零散但通用的教训

- **验证远端真实状态用 `git ls-remote`**，不要看本地 tracking ref。按 URL 直接 push 不会更新 `refs/remotes/origin/master`，`git status` 会假显示 ahead。
- **超长 commit message 用 `git commit -F <file>`**。在 csh 下，含 `§`、`→`、中文括号的超长多 `-m` 提交会**退出码 0 但根本没产生 commit**。
- **`TypedDict` 的键声明必须与它的构造点原子同批（同一次 commit）。** 加必填键 ⇒ 既有构造点全红 `[typeddict-item]`；删键 ⇒ 残留传参全红 `[typeddict-unknown-key]`。**读侧不受此限**（`.get()` 读未声明键 mypy 不报）。拆到两批之间，必然让 mypy 红一整段跨度，而各批收口门都要求 mypy 零错误。⚠ **例外面**：`mypy.ini` 已为 `reporting.py` 压制 `typeddict-item` ⇒ 该文件构造点缺键**静态检查一句话都不会说**，只能靠人工与用例守。
- **勘误要做「对称面复查」**：凡实测出某个方向的静态约束，当场问一句「反方向呢」。代价实证：sp8 把**删键**方向实测了、裁了、留档了，**却没人回头查加键方向** —— 同一份文档在同一次修订里，对同一个机制只查了一半，直到开发代理真去加键才炸出来。
- **一道防线「正确的设计」可能恰恰让它不可观测。** 判断「这道防线触发了几次」之前，先确认那个数字**是不是真被测量过**。代价实证：约束 C 的拒绝必须在写台账之前早退（否则防线自己造假绿），而 round log 只从台账渲染 ⇒ **一次拒绝在物理上不可能出现在日志里**，拿日志 grep 到的 0 与真实触发次数无关。**恒读 0 的仪器多读几次，读数还是 0，信息量为零** —— 不能拿它把「未验证」升级成「已验证」。
- **「断言某副作用不该发生」的测试，落点必须先打到 `tmp_path`；判据是红态会不会写，不是绿态。** 代价实证：`assert not Path("/tmp/evil.py").exists()` 这类写法，绿态看不出问题，**红态（正是它守的失效模式真发生时）会真往全局路径写文件**，且还原生产代码后测试仍然红，白排查一轮。
- **给用户的文字里不要写具体端口号**。VSCode 会抢注终端文本中出现的端口，僵尸转发会喂空响应导致页面空白。让用户走 PORTS 面板删旧建新、点地球图标打开。streamlit 建议加 `--server.enableCORS false --server.enableXsrfProtection false`。
