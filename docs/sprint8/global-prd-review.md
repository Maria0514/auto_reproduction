## 〇·A（现行口径）Maria 2026-08-05 拍板：全量同步，写全才能对照

**结论：`docs/sprint8/prd.md` v3.0 里已定稿的产品形态，一律写进全局产品文档正文**，每条带一个状态标注（「Sprint 8 已定稿，尚未交付」）即可。**不再区分"能力承诺"与"作废裁定"，也不再有"代码零行就不写"这条门槛。**

### Maria 原话（逐字，产品拍板）

> 「全局 prd 也是 prd，肯定优先落盘啊，应该在本 sp 的文档落盘后就回填全局文档。」
>
> 「文档就应该记录我们**所有**对产品的计划，后续才能**对照产品文档判断哪些未实现**的。**不要担心**什么写了但实际上没交付的情况。」

### 她纠正的是什么（PM 复述，确认理解到位）

原方案（§〇·B）以及它所依据的整套"交付后回填制"，都把**"文档写了、代码没做"当成病本身**，于是想靠**不写**来防。这个因果搞反了：

- **写全了，才能拿文档去对照代码、发现哪些没做**；
- **不写，那条计划就直接消失了**——连被发现的机会都没有。

⇒ **§6.2 硬件探测承诺挂 14 个月，真正的病根是"没有人拿文档去对照代码"，不是"它被写进了文档"。** 四步法逐条核对（本文 §二）、2026-08-04 那次清账，做的正是那个一直缺位的对照动作。**对照机制是解药；不写是因噎废食。**

## 〇·B（已被推翻，原文全文保留供追溯）原方案：只登记不预写

> ⚠ **本小节是 2026-08-04 的原始处置与其全部论证，已于 2026-08-05 被 Maria 整体推翻**（见 §〇·A）。原文一字未删，理由有二：①本项目写法，防"改着改着结论没了"；②它推错的那一步——**把"写了没做"当成病、想靠不写来防**——本身就是值得留档的判断失误样本，同一个误区极易复发。

### 结论

**分两类处置，界线是"这句话在代码零行时还成不成立"：**

| 内容类型 | 例子 | 本次处置 | 判据 |
|---|---|---|---|
| **能力承诺**（读者读到会认为"系统有这个"） | §7.1 MVP 功能表新增"四档判定 + 本篇成功标准"行；§4.5.2 正文改写成四档 | 🔴 **一律不写** | 代码零行时写下即超前承诺 |
| **作废裁定 / 立项事实**（陈述"这条已经不作数了 / 已经立了这个项"） | §4.5.2 卷首注记；§1.3、§4.6.1 的指向注记；§8.1 立项条目；§9.2 Q7 记入"明确不做" | ✅ **现在就写** | 代码零行时它**照样成立** |

具体落地：**§4.5.2 / §1.3 / §4.6.1 保留原文一字不动，只在旁边加注记**；**§7.1 不加 Sprint 8 行**；**§8.1 加 sp8 立项条目**，措辞严格用"立项"体并显式写明"代码零行、尚未交付"。

### 五条理由（原方案的论证，已随原方案被推翻，保留供追溯）

**1. 底线优先：绝不能把还没做的写成已经做了。**
四档制代码零行，2026-08-04 上磁盘核实：`ui/term_map.py:84-86` 仍是 `conclusion_level:science` / `:engineering` / `:none` 三条两档文案；`core/nodes/reporting.py:245` `_determine_conclusion` 仍按两档判。§6.2 那条硬件探测承诺蒸发七个 Sprint，根因就是"文档描述的是应有形态，写下不等于做了"。**不能一边清这笔账，一边开一笔新的。**

**2. 但"什么都不写"同样有害，而且是同一个病的另一面。**
sp8 PRD v3.0 **显式判定**全局文档 §4.5.2 整条作废重写、§1.3 两档名整体作废（`docs/sprint8/prd.md` §3 第 1/2 项）。一条已定稿的作废裁定如果只活在 sprint 文档里、全局文档正文一个字都不标，读者就会继续把一个已知作废的定义当成当前真理来用——**这与本次 C 档要结清的「兼容性维度的 backlog 只登记在 `docs/sprint7/prd.md:780`、全局文档正文没标」是逐字同型的病**。不能一边结清它、一边制造一条新的。

**3. §7.1 不入行的直接先例就在六天前，而且是本文件自己立的。**
2026-07-29 那次同步为 S7-08 立过一条：「PRD §10 与架构 §18 均已定稿，但**代码零行** ⇒ 按回填制不写进全局文档」（`docs/sprint7/global-prd-review.md:10`）。这条制度建立第一周就破例，它等于没建。

**4. ⚠ 必须订正一个流传中的说法：sp5 / sp6 的先例并不是"代码已交付才同步"。**
本次上磁盘核实：`docs/sprint5/prd.md:4` 日期 2026-07-08，全局文档 v0.2 → v0.3 的更新日志也是 2026-07-08，**同一天**，措辞是"立项修订"；`docs/sprint6/global-prd-review.md:3` 产出于 2026-07-13，全局 v0.3 → v0.4 同样是 2026-07-13，同样写"立项修订"。⇒ **sp5 / sp6 两次都是在立项当天、代码尚未交付时就把 §7.1 MVP 表和 §8.1 路线图一起写了。**
所以本次不是"跟随先例"，而是**在两条互相冲突的先例之间做选择**：取严的那条（sp7 的 S7-08 回填制），舍宽的那条（sp5/sp6 的立项即入表）。**取严的理由**：本项目此后踩的坑——§6.2 硬件探测挂 14 个月、§4.5.2「与论文报告一致」从 Sprint 5 挂到今天、§5.4 CLI 四条命令全不存在——**无一例外全部出在"宽"那一侧**。没有一次是因为写得太保守而出事。

**5. 与 2026-07-28 我自己否掉的那个折中方案的关系（必须说清，否则像打自己脸）。**
当时我否掉了"给全局文档加一个『已立项待交付』标注"的方案，理由是**会给活文档新开一套此前不存在的中间状态体例**。

- **该理由在 2026-07-29 之后已经不成立**：那次同步亲手在本文件里建起了这套体例——§6.2 第 2 句「本条尚未实现，已转 backlog」、§5.4 节首「设计构想，尚未实现」、§7.1 CLI 行「~~P1~~ **暂不排期** + 尚未实现」。体例既已存在，"不新开体例"就不再是拒绝的理由。本次的注记全部沿用这三处的现成写法，**没有新造任何格式**。
- **但当时那个方案的核心，本次依旧否掉**：那个方案是给 sp8 的**新能力**在 §7.1 里预先占位（"已立项待交付"）——本次**不做**。本次做的是给**已经在文档里、已被判作废的旧描述**加失效标注。**前者是预写未来，后者是止损当下，方向相反。**

### 由此产生的两条硬性后续（不登记就是下一次蒸发）—— ⚠ 已随原方案作废：两条内容均已于 2026-08-05 直接写进全局文档正文

# 七、写全之后：怎么保证真有人去对照（PM 建议，2026-08-05 新增）

> Maria 的诉求是「后续才能**对照**产品文档判断哪些未实现」。**写全只是前提，"有人真去照"才是那句话的后半程。** 本节五条**全部零新机制、零新文件、零新工具**，只是把对照动作绑到已经存在的触发点上。

## 1. 标注做成可 grep 的单一字符串（本次已落地）

全局产品文档里未兑现的承诺**只用一种写法**：「Sprint N 已定稿，尚未交付」。不做状态枚举、不做多档分类。⇒ 任何人一条 grep 就能得到当前未兑现承诺的**条数**（2026-08-05 落盘后实测：`grep -c` 命中 **26 行 / 30 处**，覆盖 §1.3 / §3.2 步骤 5-7 / §4.3.1 / §4.3.2 / §4.3.3 / §4.4.0 / §4.5.2 / §4.5.3 / §4.6.1 / §5.2 页面 3 / §7.1 / §8.1；其中文末更新日志 1 处属元数据、不计承诺）。**这个数字本身不精确到"一条承诺一次命中"，也不需要精确**——它的用途是给出量级、并让"还欠多少"随时可查，不是当 KPI 用。

**建议**：把这个数字**纳入每个 Sprint 收口的必报项**，与回归用例数同级。它不需要任何工具，但把"还欠多少"从"得翻文档才知道"变成"一个数"。

## 2. 核销动作绑到已有的批次边界（不新增流程）

本项目已有铁律「批次边界逐批确认」（`docs/MEMORY.md` §3.3）。**建议在每批交付确认时多问一句：「这批把全局文档里哪几条『尚未交付』标注摘了？」** 摘标注必须附 `文件:行号`。

⇒ 对照动作有了**固定触发点**，不再靠人想起来。`docs/sprint7/global-prd-review.md:141` 那份 9 条清单无人认领六天，根因正是它没有绑在任何触发点上——**没有触发点的待办等于没有待办。**

## 3. 清单语义由"待写"改成"待核"（本次已落地，见 §四）

`global-prd-review.md` §四 以前是"待回填清单"——**写完就没人管了**；现在是"待核销清单"——**只要还有条目没核销，Sprint 就不算收口**。

一字之差，决定这份清单是"一次性任务"还是"持续闸门"。

## 4. 下一个 Sprint 的 PRD §3 核对表增加一条硬性输入

现行四步法第 1 步是「按本次主题在全局文档里检索相关章节」——**依赖检索是否周全**，而检索周不周全是没法验证的。

**建议加一条无条件规则**：把上一版全局文档里**所有带"尚未交付"标注的条目，不经判断、全部列进本轮核对表**，逐条三选一（已实现 / 本次纳入 / 明确不做）。

⇒ 漏掉的可能性从"检索够不够周全"降到"有没有做这一步"，**后者好查得多**——前者要复盘思路，后者只要看表里有没有那几行。

## 5. 摘标注的 commit 必须留痕（一条反向保险）

**建议**：摘除某条"尚未交付"标注的那次 commit，message 里带上被摘的章节号（如「摘除 §4.5.2 四档制标注，依据 `ui/term_map.py:84-87`」）。⇒ `git log --grep` 就能回溯"**这条承诺是什么时候、凭什么被认定兑现的**"。

**为什么需要这条**：2026-08-04 清账挖出过一条**假的"代码未交付"**——技术架构文档挂着说某个缺口未修，而代码早就修好了（`core/nodes/resource_scout.py:68` 已是 2600）。它能存活，正是因为**摘不摘标注这件事本身没有任何留痕**：没人能查出它该在哪一次被摘掉，于是它就一直没被摘。

> **五条的共同点**：都不新增机制，只是给已经存在的动作加触发点和留痕。**Maria 反对过度工程**（`docs/MEMORY.md` §4.1）——对照机制如果自己长成一套需要维护的系统，它会先于承诺蒸发掉。
